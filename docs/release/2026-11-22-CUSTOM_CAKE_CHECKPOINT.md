# Custom-cake and order-history repair evidence

The secondary authenticated customer, bakery and administrator pages now support persisted custom requests, bakery-entered quotations and deposit requirements, customer quote acceptance, and guarded production states. Prices and deposits are entered explicitly by the bakery; no commission or deposit percentage is invented. Stable request IDs prevent duplicate retries. Online payment mutations fail closed. Confirmed balance values come from the existing payment ledger, not client claims.

The feature remains disabled (`CUSTOM_CAKES_ENABLED=false`). Proposed migration 007 restores definitions of the already inspected staging custom-cake tables for fresh database reconstruction. Proposed migration 010 adds narrowly scoped customer acceptance/cancellation protections and a server-only approved-bakery lock helper. Review its grants against the actual API database role before application. No remote migration has been applied. Activate only after schema review, staging migration approval and real-role acceptance. Rollback instructions are in custom-cake-customer-decisions.rollback.sql and preserve existing records.

Confirmed defect: suspended-shop RLS hid customers' existing order history through inner joins. Protected reads and SELECT policies now retain owned order history through left joins while keeping suspended shops undiscoverable and outsiders denied. Migration 011 and its captured-policy rollback remain proposed only; neither changes stored rows.

Local evidence: five PGlite/API/JWT tests cover persistence, duplicate and altered retries, role isolation, stale quotations, customer finance tampering, pending versus fixture-confirmed ledger balances, feature/migration fail-closed behavior and suspended-shop history. These use isolated fixtures, not live payment providers. Two browser fixtures cover secure retry IDs, old-session response suppression and bakery Rand-to-cents entry. Existing demo/preflight tests are retained.

Still blocked or absent: reviewed staging migrations and runtime grants, verified customer/bakery/admin staging accounts, live source-matched browser transactions, payment-provider sandbox confirmations/refunds, custom-image storage, dedicated custom-order notifications, business-approved minimum lead times and fulfillment/contact arrangements, backup restoration acceptance and human-device testing. Requested event dates are stored for bakery review; no unapproved lead-time policy is inferred. This is not a beta-ready or payment-ready declaration.
